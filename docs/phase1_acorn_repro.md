## 2. Selected benchmark and why

**ACORN paper §7.3.1, LCPS benchmark on SIFT1M** (Fig. 7a; Table 3 SIFT1M
column; structural cross-checks against Tables 5 and 6, SIFT1M column).
Methods reproduced: **ACORN-γ** and **ACORN-1**. (HNSW post-filter and oracle
partitions in Table 3 are baselines, not ACORN; out of scope for Phase 1.)

Why this one, against the four criteria:

| Criterion | SIFT1M (chosen) | Paper | TripClick | LAION-1M/25M |
|---|---|---|---|---|
| Dataset availability | Public; already on disk, SHA-256 verified (Project 1) | Public (NHQ release), 2M×200, not on disk | Raw text public; vectors must be re-encoded with DPR by us | Captions/CLIP public; keyword lists must be regenerated by a CLIP-scoring procedure we'd re-implement |
| Ground truth | Computable exactly from a fully specified attribute model | Same | Depends on our encodings | Depends on our keyword lists / regex sampling |
| Reproducibility of settings | Fully stated: random int 1–12, equals(y), γ=12, M=32, Mβ=64, K=10; also in the authors' driver (`run_simple_test.sh`) | Same | Query sampling / workload construction under-specified | Workload generation under-specified |
| Direct numeric comparison | **Table 3** (hardware-independent distance counts), **Table 6** (graph structure), Table 5 (size), Fig. 7a (QPS) | Table 3, 5, 6, Fig. 7b | Figures only + structural tables | Figures only + structural tables |

SIFT1M is not chosen for being easiest: Paper has the same specification
quality and comparable tables. SIFT1M is chosen because (a) it is the only
dataset where the full chain — vectors, attribute model, predicate, ground
truth — is reproducible without re-creating any data the paper's authors
generated themselves, (b) Table 3 gives a **hardware-independent** effort
number (distance computations at fixed recall), which is exactly the
primary effort measure of this project (design doc §12), and (c) it is the
project's own core dataset (design doc §11), so the reproduction directly
validates the baseline we will build on.

## 3. Exact configuration

### 3.1 Data
- Base: `data/sift/sift_base.fvecs` — 1,000,000 × 128 (float32 of integer
  values 0–255). SHA-256 verified by `scripts/download_sift1m.sh`.
- Queries: `data/sift/sift_query.fvecs` — **all 10,000**, file order. (Paper
  §7.1.1 states SIFT1M has 10K queries and, unlike TripClick/LAION, does not
  mention sampling → all 10K.)

### 3.2 Attributes and predicate (paper §7.1.1)
- Base attribute: i.i.d. uniform integer in {1,…,12} per base vector.
- Query attribute: i.i.d. uniform integer in {1,…,12} per query.
- Predicate: `equals(y)` — base vector passes iff its attribute == query's.
  Expected selectivity 1/12 = 0.0833 (Table 2: 0.083).
- RNG: `std::mt19937_64` + project-side unbiased rejection sampling (not
  `std::uniform_int_distribution`, whose output is library-specific).
  - **Draw A (primary):** base seed 20261002, query seed 20261003.
  - **Draw B (sensitivity):** base seed 20261102, query seed 20261103.
- The paper's own draw / seed is unpublished → exact-attribute reproduction
  is impossible; draw-to-draw variation is measured (Draw A vs B) instead.

### 3.3 Index construction
| | ACORN-γ | ACORN-1 |
|---|---|---|
| γ | 12 | 1 |
| M | 32 | 32 |
| Mβ | 64 | 64 (= 2M) |
| efConstruction | 384 (= M·γ, ACORN default) | 32 (= M·γ, ACORN default) |
| metric | L2 | L2 |
| ACORN RNG seeds | level RNG 12345, insertion-order RNG 789 (hard-coded in ACORN) | same |
| build threads | 16 (OpenMP default = all) | 16 |

**Paper-text vs released-code conflicts, resolved before any run:**
1. *efConstruction.* Paper §7.2: ACORN uses "M and efc the same as HNSW
   post-filtering", i.e. efc = 40. Released driver `test_acorn.cpp` sets
   efc = 40 only on the plain HNSW index and leaves ACORN at its constructor
   default efc = M·γ. **Table 6 decides it:** SIFT1M ACORN-γ level-1 average
   out-degree is 384 = M·γ (full lists). Candidate lists during insertion are
   bounded by efc, so with efc = 40 a node gets ≤ 40 forward links plus
   reverse links, averaging ≤ ~80 — 384 is unreachable. Only efc ≥ 384 is
   consistent with the paper's own Table 6. → **efc = M·γ (code default).**
2. *ACORN-1 Mβ.* Paper §7.2: "fix γ = 1 and Mβ = M" (= 32). Driver:
   `IndexACORNFlat(d, M, 1, metadata, M*2)` (= 64). **Table 5 decides it:**
   ACORN-γ 0.98 GB vs ACORN-1 0.93 GB. Estimated sizes: storage 0.512 GB +
   level-0 lists (Mβ+1.5M)·4 B·1M + upper levels. Mβ = 64 ⇒ gap ≈ 0.045 GB
   (upper-level M·γ lists only); Mβ = 32 ⇒ gap ≈ 0.17 GB. Observed 0.05 GB
   ⇒ **Mβ = 64 (driver value).**
3. Rule for anything else: follow the authors' released driver.

### 3.4 Search
- K = 10. `efSearch` set via `index.acorn.efSearch`; ACORN uses
  ef = max(efSearch, K).
- **Paper grid** (curves, QPS): efs ∈ {10, 60, 110, …, 760} (paper: "10 to
  800 in step sizes of 50") — 16 values.
- **Dense grid** (Table-3 crossing): efs ∈ {10, 11, …, 200}. If recall@10
  is still < 0.8 at efs = 200, the crossing is taken from the paper grid.
- Filter: ACORN's `filter_id_map` (nq × N bytes, row-major [query][base]),
  exactly as in `test_acorn.cpp`; built outside any timed region.

### 3.5 Metric definitions
- **Ground truth:** exact filtered top-10 per query by brute force over the
  base vectors passing the query's predicate; squared L2; ties broken by
  smaller id. SIFT values are integers ≤ 255, so every squared distance
  (≤ 128·255² < 2²⁴) is exact in float32 — ties are exact and detectable.
  Queries with a tie at the 10th/11th position are counted and reported.
- **Recall@10** = |R ∩ G| / 10 per query, R = returned ids, G = GT ids
  (paper §3: recall@K = |G∩R|/K; same as ACORN's `compute_recall`).
  Reported as the mean over queries.
- **Distance computations per query** = ACORN's own counter: the increase
  of `faiss::acorn_stats.n3` during that query's search (upper-level greedy
  descent + level-0 search). Mean = n3 / n1, the quantity `test_acorn.cpp`
  prints as "average distance computations per query". Collected by calling
  `search` with n = 1, single-threaded (the global counter is updated
  unsynchronised, so this must not be done in parallel).
- **Table-3 value (distance computations to achieve 0.8 recall):** on the
  union of both grids, take the first adjacent pair (efs_lo, efs_hi) with
  mean recall < 0.8 ≤ mean recall, and linearly interpolate mean distance
  computations in recall to 0.8. Also reported: the value at efs_hi
  (no interpolation). The paper does not state its procedure; this is the
  pre-registered choice.
- **QPS:** batch `search` over all 10K queries with 16 OpenMP threads (all
  hardware threads, as the paper used all of its machine); 1 untimed warm-up
  + 50 timed trials (paper: "QPS averaged over 50 trials"); QPS = 10,000 /
  wall time. Mean reported (paper), median and stdev also kept. Paper grid
  only.
- **Per-query latency (secondary):** single-thread wall time of each n = 1
  search call during the per-query pass.
- **Out-degree per level:** for each node present at level ℓ, the number of
  distinct valid neighbour ids in its level-ℓ list (stopping at the first -1),
  averaged over those nodes — the same computation as ACORN's
  `print_neighbor_stats(level)`.
- **Index size:** (a) serialized `write_index` file size, (b) in-memory size
  of storage + neighbour/offset/level arrays. Reported in GB (1e9) and GiB.
- **TTI:** wall time of `index.add(N, xb)`, 16 threads.

## 5. Pre-registered comparison criteria

Exact reproduction of the paper's numbers is not possible even in principle
(unpublished attribute draw; ACORN's multi-threaded build is
non-deterministic). So:

- **Hardware-independent (pass/fail):**
  - Table 3: |ours − paper| / paper ≤ **10 %** for both ACORN-γ and ACORN-1,
    and ACORN-γ < ACORN-1. 10–25 % = "close, investigate"; > 25 % =
    discrepancy that must be explained before the checkpoint is met.
  - Table 6: levels 0–2 within **10 %**. Level 3 (≈ 1M/32³ ≈ 30 nodes) and
    level 4 reported, not judged.
  - Table 5: within **10 %**, but only after confirming the unit/measure
    the paper used is the one we compare against; otherwise reported only.
- **Hardware-dependent (reported, not pass/fail):** QPS curve and TTI. We
  check only the qualitative shape: ACORN-γ ≥ ACORN-1 QPS at fixed recall,
  recall range comparable to Fig. 7a.
- **Variation baselines** used to interpret any gap: build A vs build B
  (same config, independent builds) and Draw A vs Draw B.

## 6. Correctness and reproducibility checks

1. Filtering: every returned id passes the query's predicate (or is -1);
   zero violations required.
2. Returned distances equal our recomputed squared L2 for those ids.
3. Ground-truth code: (a) unit tests vs. a naive reference on toy data;
   (b) with an all-pass filter on SIFT1M, our top-10 equals the official
   `sift_groundtruth.ivecs` top-10 (modulo exact ties, reported);
   (c) filtered GT for 200 queries cross-checked against FAISS
   `IndexFlatL2` built over the filtered subset (independent code path).
4. Recall: unit-tested on hand-built cases.
5. Distance counter: sum of per-query (n = 1) n3 deltas equals the n3 delta
   of one batch call over the same queries at the same efs.
6. Search determinism: repeating the per-query pass gives identical ids and
   identical per-query distance counts.
7. Serialization: an index reloaded from disk (with metadata pointer
   re-attached) gives identical results to the in-memory index.
8. Build-to-build: ACORN-γ and ACORN-1 each built twice (A, B); Table-3 value
   and out-degrees compared.

### 8.8 Discrepancy investigation

**Classification of every comparison:**

| Quantity | Class |
|---|---|
| Table 6 levels 1, 3, 4; level counts | exact reproduction |
| Table 3 ACORN-γ (−4.0 … −4.9 %), Table 6 levels 0, 2 (−5.4 %, −2.8 %), Table 5 (±5 %) | expected differences (unpublished attribute draw, non-deterministic parallel build, unstated Table-3 procedure) — within pre-registered tolerance |
| TTI, QPS | expected hardware/environment differences (16 vs 96 vCPUs; shared VM, D3) |
| **Table 3 ACORN-1 (−9.5 % primary; −9.8 %, −10.1 % in variation runs)** | **not fully explained** — at the pre-registered 10 % boundary, systematic |

**What was ruled out for the ACORN-1 gap (no parameter changes made):**
1. *Noise.* Build-to-build and draw-to-draw variation is ≤ 0.7 %; the gap
   is ~14× larger and has the same sign in all runs → systematic.
2. *Ground truth / recall definition.* GT verified three independent ways
   (§8.4); recall is the paper's id-based definition; only 20 queries have
   rank-10 ties.
3. *Counter definition.* ACORN's filtered search only fills `n1` and `n3`
   (`impl/ACORN.cpp` lines 1400–1404, 1545); `ndis` is never set on this
   path. We use n3 / n1 — exactly what `test_acorn.cpp` prints as "average
   distance computations per query". Counter verified (§8.5).
4. *Table-3 interpolation procedure.* Interpolating on the paper's coarse
   curve grid (efs 10 → 60) instead would give +48.6 … +50.4 % (γ) and
   +22.9 … +24.2 % (1) — far from the paper — so the paper must have used a
   fine grid like ours. Using the uninterpolated upper bracket instead gives
   −3.4 % (γ) and −8.5 % (1) for the primary run: the gap is not an
   interpolation artefact.

**Not tested (would require running parameter variants — needs approval):**
- ACORN-1 efConstruction: we use the code default M·γ = 32 (the authors'
  driver leaves it unset); paper text says 40. No published number
  discriminates between them (unlike efc for ACORN-γ, settled by Table 6).
- ACORN-1 Mβ: we use 64 (authors' driver; supported by Table 5's 0.05 GB
  γ − 1 size gap, which we reproduce: 0.0455 GB); paper text says Mβ = M = 32.
- Code version: the public repository's first commit (2024-04-10) post-dates
  arXiv v1 (2024-03-07); the paper's numbers may come from earlier code.
- Query subset: the paper does not say whether all 10K queries were used.

ACORN-γ shows the same sign of gap (−4 to −5 %), which is consistent with a
common factor (e.g. code version or query set) affecting both methods, but
this is not established.

## 9. Deviations from the pre-registration

All deviations are procedural; none changes a dataset, parameter, grid,
metric definition or acceptance criterion in sections 3–5.

- **D1 — pipeline split into stages; sweeps run in parallel (user-approved,
  2026-10-02).** Attempt 1 (single process, everything sequential) was
  stopped by the 2-hour background-task limit after completing the ACORN-γ
  per-query sweep. The per-query pass must be single-threaded (ACORN's
  distance counter is an unsynchronised process-wide global), so the full
  plan needed ~10–12 h sequentially. The driver was split into stages
  (`gt_checks`, `build`, `sweep`, `verify`, `timing`), each a separate
  process, run detached by `scripts/run_phase1.sh`: GT checks and builds run
  alone, then the 6 sweeps (3 runs × 2 methods) run concurrently, one
  single-threaded process each, then verify + timing run alone, one at a
  time. Consequences:
  - Recall, distance counts and returned ids are unaffected (search is
    deterministic; verified by the `verify` stage, which re-runs queries in
    a fresh process and compares with the sweep's recorded output).
  - **Per-query latency** (a secondary metric, §3.5) is measured with up to
    5 other single-threaded sweeps running concurrently on the 16-vCPU VM,
    so it is not a clean single-thread latency. QPS (batch, timing stage)
    still runs alone, as pre-registered.
  - In the sweep stage each query's filter row is built per query (outside
    the timed call) instead of slicing the nq × N map; the bytes are
    identical. `verify` checks that the batch call on the full nq × N map
    returns the same ids as the per-query sweep.
- **D2 — ACORN-γ build A reused from attempt 1.** Its TTI (1314.8 s, 16
  threads) is taken from attempt 1's log
  (`results/phase1/attempt1_killed/logs/buildA_drawA.log`); the index file
  is the one attempt 1 saved and reload-checked (identical results). The
  primary config's `reuse_cached` is therefore `true`. Attempt 1's raw
  outputs (complete ACORN-γ sweep, partial timing) are kept in
  `results/phase1/attempt1_killed/` and are compared with the new sweep as
  an extra cross-process determinism check.
- **D3 — QPS timing: shared-machine contention; follow-up timing skipped
  (user decision, 2026-10-03).** The VM is shared: during the timing stages,
  Project 1 (`ann_router_staleness`) Phase 5 jobs from another session were
  running (`ars_check_state`, `phase5b_checks.py`; load average ≈ 28 on 16
  vCPUs). The pre-registered "QPS must run alone" condition was therefore
  **not met**; trial-to-trial spread at a fixed efs is 2–3× (e.g. ACORN-γ
  efs 210: 7.4–19.7 s per 10K-query batch). My runtime estimate for the
  timing stage was also wrong by ~20× (each method's 16 efs × 51 batches
  takes ~5 h here, not ~15 min). The orchestrator was stopped after the
  primary run's timing stages; the remaining 4 verify stages run via
  `scripts/run_phase1_verify_rest.sh`; QPS timing for the build-B and
  draw-B runs is skipped. Primary-run QPS is reported with this caveat and
  is to be re-measured on an idle machine later. Recall, distance counts and
  structure are unaffected (hardware-independent; determinism verified).
